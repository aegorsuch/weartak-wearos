# Position log

Position logging is separate from application diagnostics and is disabled by default.
Enabling it in Developer Options records the watch UID and GNSS fixes in app-private
storage. Export is explicit; the CSV contains sensitive location history.
Storage retains at most 50,000 fixes, discarding older entries and flagging the
log as incomplete when retention removes entries.

The timestamp is the Android fix time in UTC (ISO 8601). Coordinates are WGS84
decimal degrees. `horizontal_accuracy_m` is Android `Location.accuracy`, the
estimated 68% horizontal confidence radius in metres, not ground-truth error;
it is empty when unavailable.

Disposition reflects observed transport handoffs, not confirmed receipt.
`sent_immediately` means the first observed handoff occurred on the fix's first
PLI dispatch attempt, both attempt and handoff within one configured reporting
interval of the fix and before another PLI dispatch. `buffered_sent_later` means
a later dispatch attempt, or an attempt or handoff outside that interval or
after another dispatch; this includes a fix
retained as the latest position, not necessarily a durable transport queue.
`first_handoff_timestamp` and `first_handoff_bearer` identify that first observed
handoff. A newly generated callback rejected before selection for reporting is
`never_sent` while it remains unselected; a later selection changes that status.
Cached fixes predating capture, fixes with unobserved results, and fixes offered
to plugin or companion routes remain `unknown`. A successful handoff through
another tracked route does not eliminate uncertainty from those routes.
`untracked_offers` identifies these plugin and companion offers, not successful
transmission; multiple routes are separated by semicolons.
These classifications are incomplete and may change as asynchronous operations
complete; an export is a snapshot. Relay information is not exposed and is blank.

A successful direct TAK Server or multicast socket write adds
`TAK_SERVER` or `MULTICAST` to bearer and `socket_written` to its status;
`write_unconfirmed` means no successful write was observed; a failed write
may have sent part of a message. A
SITX WebSocket accepting a message into its send queue adds `SITX` and
`api_accepted`; `not_accepted` means no socket accepted it or the command
queue rejected it. A blank status means no result was observed, not failure.
Bearer lists only observed successful handoffs, separated by semicolons; other
routes are not tracked. Neither a socket write nor API acceptance confirms
receipt. Only snapshots whose coordinates match the original location provider
are correlated. The
recorder observes active Android location callbacks, not fixes generated by
hardware or other devices outside those callbacks. Repeated callbacks for the
same provider, fix timestamp, elapsed time and coordinates are deduplicated.
The incomplete-storage warning persists after a queue or storage failure; an
export remains available for recovering the records that were saved. Queued
fixes may be lost on abrupt process termination.

For tracked routes, `*_attempts` counts observed route submissions per fix,
and `*_pending` counts submissions for which the journal has not observed a
completion. TAK fan-out counts each eligible server separately. Pending does
not prove work is still in flight: callbacks can be lost when a service stops,
the process dies, or logging is disabled. A SITX command can also be dropped
without a callback when no service is collecting its command bus. Pending
records are retained across restart, bounded to 10,000, and deleted with their
fix. At the limit, the oldest pending identity is replaced, its unresolved
count remains visible, and the log is flagged incomplete because a late
callback for that identity can no longer be correlated. Counts for fixes written
before route accounting was introduced start at zero and do not describe older
attempts. A missing fix or a zero count does not prove a route was unavailable.
Plugin and companion offers remain untracked and do not contribute to these
counts. Failed or pending attempts cannot establish `never_sent`. If any
storage or correlation failure flags the log incomplete, exports suppress
`never_sent` for all fixes because missing events could change that conclusion.

Developer Options can export the CSV or create a ZIP with a TAK mission-package
manifest, CSV, application diagnostics and a privacy note. The system document
picker is required for file export. Alternatively, upload the package to a
selected connected TAK Server; this does not notify recipients, so share the
displayed SHA-256 hash separately. Server permissions control who can retrieve
the upload. Offline transfer without a document provider and delivery results
for plugin or companion routes are not implemented.
